# Allura core — private isolated release v0.1.0-dev.1

This is the current rebuilt core, not the historical deployed service or UI. Runtime is exactly Bun 1.3.14 / Node 24.19.0 on supported Linux with pinned native RuVector/ONNX dependencies, PostgreSQL 16.15 and the pinned 384-dimensional MiniLM model. The source package name remains the private foundation workspace; the distribution contract is `allura-core-release-v1`. It is not an npm publication.

## Install and initialize a new, empty isolated instance

Verify the archive SHA256 against the pack receipt from the trusted source checkout, then extract into a new owned directory. The receipt records actual source HEAD, dirty status and all shipped file digests; dirty builds are explicitly not exact-revision releases. Runtime verifies shipped input hashes before connecting to the database. Checksums are integrity evidence, NOT signatures, and do not authenticate a modified manifest, dependencies or model cache.

Run `bun run install:frozen`, then `bun run prepare:model`. The latter explicitly downloads the pinned public model revision and exercises CPU inference; it refuses model-token environment variables. Server inference is offline and fails closed if preparation is absent. Installation does not copy pre-existing node_modules or substitute stub vectors. Model files and ONNX/native dependencies require local disk and memory; production sizing is not established by fixture tests.

An authorized operator must provision a NEW local PostgreSQL 16.15 instance/database. Initialization is never performed implicitly by server startup. Inject `ALLURA_INIT_DATABASE_URL` (postgres owner URL, loopback only, never a template/default database) and a freshly generated 32-byte hexadecimal `ALLURA_INIT_APP_PASSWORD` through a private environment, then run `bun run init:empty`. Do not put values on command lines or in source/configuration/logs. This applies the shipped checksum-bound migrations and enables the restricted allura_app login. It refuses any existing application role, user schema/object/extension or initialized database. It creates no people, workspace grants, memory or approved knowledge. Do not point this command at a shared or production database. If initialization fails after migrations but before login setup, discard the explicitly owned fresh fixture; do not assume rollback of the whole procedure or retry against an occupied target. Existing-instance migrations require a separately authorized operational procedure, not this initializer.

Remove owner initialization variables before starting the application. Inject only `ALLURA_DATABASE_URL` for restricted allura_app on loopback, and `ALLURA_CURSOR_KEY`, exactly 32 random bytes encoded canonical base64url. Keep the cursor key stable across restarts and rotate via an explicit operation (old cursors expire/reject). Never supply the owner credential to the running server. Database roles with superuser/bypass/create/inherit/membership/ownership powers are rejected before listen.

Write a public configuration JSON file with exactly: `origin` (canonical HTTPS origin); `issuer` (exact https://TEAM.cloudflareaccess.com issuer); `audience` (Access application audience); `port` (0 for ephemeral local fixtures, otherwise explicit port); `keys` (1–8 distinct `{kid,pem}` entries containing RSA public SPKI keys of at least 2048 bits). No private key or credentials belong here. Obtain the real public keys through a separately authorized identity-provider configuration; fixture keys are not production credentials. This bounded release uses explicitly configured public keys, not an automatic JWKS refresher: rotation requires config replacement and restart. Identity bindings and initial eligible human membership must be provisioned through the separately authorized onboarding process; initialization does not invent a user, grant access or bypass independent human approval.

Run `bun run start ./config.json`. Startup verifies the release, restricted role, schema presence and offline model before binding ONLY 127.0.0.1. Its single JSON readiness line reports actual port/source; no credential is printed. Gateway endpoints include authenticated machine POST `/mcp`, signed-human `/mcp/human`, and current scoped API routes. Public GET `/health/live` reports only `{"status":"up"}`; it is process liveness, NOT authenticated dependency health or retrieval readiness. Content and scoped health require authorization; no generic REST capture route is provided. Capture is evidence, not approval. Use the separately packed consumer SDK/CLI/stdio contract; insecure loopback client allowance is a fixture-only opt-in. External routing/TLS/Cloudflare, deployed identity onboarding, production secrets and publication are separate authorization boundaries. No deployed hostname is claimed by this package.

SIGTERM/SIGINT stop the server and close database connections with a five-second bound. A deadline is a failure/unknown outcome, not proof a write rolled back; recover ambiguous mutations through their exact idempotency/receipt contract. A real process restart must use the same database and stable cursor key. PostgreSQL ephemeral Docker port assignments may change after restart: rediscover the actual binding and update the injected connection URL, never silently reconnect to an unrelated service.

## Browser operator surface (local implementation)

The same packed core serves `/dashboard` and its `/assets/` bundle. Open `/dashboard` at the explicitly configured HTTPS origin after authorized TLS/Access routing and human onboarding have been supplied. The shell is public static content; opening it grants no workspace or memory access. Use the browser-managed signed HttpOnly Access cookie; do not paste a JWT, device token or password into this UI. Enter the exact tenant namespace and workspace UUID, then choose **Open workspace**. These are routing selectors, not grants; the active scope and currently checked human role are displayed separately. No default workspace is guessed.

Company Knowledge provides bounded current/history lists, search, exact-version inspection and correction proposals. Review changes displays pending/needs-evidence proposals, their linked source evidence and independent approve/request-evidence/reject decisions. Confirmations show the version/rationale; inspect the returned receipt. Capture still uses the enrolled device/agent SDK or MCP. Initial proposal submission is not idempotent: after an unknown result reconcile the queue rather than blindly creating another proposal. Explicit exact-operation retries are offered only for supported operation-key mutations; they do not assert current state or undo a later decision.

Administration submits existing governed access/consent commands and reads their outcome. Organization membership may request access without receiving content; admin powers and independent approval remain server-enforced. Devices & agents lists owner-scoped public metadata, permits current admin enrollment approval and scoped revocation; enrollment completion/rotation and raw secrets stay in the secure-store client. Search settings probes actual scoped readiness and can run one bounded indexing job. Audit & Operations exports at most100 freshly authorized observations, not an exhaustive historical audit or remote publication. Security & Trust explains the current immutable policy and allowed actions; it does not offer policy override switches.

All reads/mutations recheck current server authority. Denial clears previously displayed scoped content; navigation discards late replies and stops subsequent stale inspector work. Unknown outcomes do not imply success or rollback. The interface uses local Plex fonts, retained AL artwork, keyboard-operable confirmations and responsive navigation. Actual human usability/deployed acceptance is still separate from automated Chromium checks. Memory Map is truthfully pending Story9.3 in this candidate; do not mistake that placeholder for an interactive graph. Work boards/runs/telemetry and unadopted optional modules are not supplied. This README does not authorize deployment, production onboarding or release promotion.

## Human proposal submission and manual indexing

All routes below are POST with `Content-Type: application/json`, exactly one `group_id` and one `workspace_id` query parameter, and a valid signed human Access assertion or authorization cookie. Supply the configured HTTPS `Origin` AND `Sec-Fetch-Site: same-origin`. A machine bearer credential cannot invoke these human routes. Scope parameters select a requested scope, never confer authority. The server checks current membership/action grants before and after service work; requester/actor/role fields in JSON cannot override them. Responses are the service object directly, not wrapped in a `data` field.

`/api/review/submit` requires `proposal:write`. Its JSON fields are `summary` (nonempty, at most 12000 UTF-8 bytes), `assertionKind` (`observation` or `inference`), `evidenceIds` (1–32 distinct authorized event UUIDs), and optional `confidence` (finite 0–1). Unknown fields are rejected. To revise a proposal, also supply its `proposalId` and the exact `expectedVersion`; both are omitted for initial submission. Read the returned `id`, `version` and `state`. Neither confidence 1 nor evidence capture promotes anything: a separate independently authorized human must review the exact proposal version through the existing review/decision contract. Submitter access does not imply access to another actor's unlinked raw capture; denial is not a reason to widen workspace grants. Initial proposal submission has no capture-style idempotency key: do NOT automatically retry an ambiguous lost response and assume a duplicate was avoided. Exact-version revisions conflict if the base changed; decision retries use their original operation key and payload.

`/api/index/drain` also requires `proposal:write` and accepts exactly `{}`. It attempts at most ONE eligible current-scope event/semantic job per request using the pinned local embedder and existing lease/fencing rules, returning `{"jobs":[...]}` with each attempted job's `kind`, `id` and `state`. No limit, source ID, principal or authority override is accepted. This is an explicit manual trigger, not a background daemon or automatic indexing on capture/approval. Repeated requests can process additional eligible jobs; an empty list only means none were eligible in that request, not that no delayed/retrying/failed work exists. Inspect actual job states and authorized scoped health. A successful HTTP response alone does not mean a vector became usable; verify retrieval's actual `used`/`degraded` metadata and expected current record.

Index work is finite and cancellation-aware. Pre-aborted requests cannot claim work; cancellation or provider failure cannot publish a late successful vector. Retry eligibility/attempt ceilings remain server-controlled. A request deadline or connection loss is still an unknown caller outcome: it does not prove a transaction rolled back. Query current authorized observations rather than asserting success or launching unbounded retries. Indexing never bypasses independent human approval or turns pending/raw content into current semantic knowledge. Graph evidence expansion separately requires evidence authority, not merely memory-read permission.

## Device enrollment and credentials

POST `/api/devices/command` uses the SAME signed-human/CSRF/scope requirements above, not a machine bearer or anonymous pairing endpoint. Body is one exact command from `src/device-contract.ts`: `begin`, `approve`, `complete`, `status`, `rotate`, `revoke` or `list`. Initial admission requires current memory-read; `approve` additionally requires an explicitly granted human workspace administrator. Organization administration alone grants nothing. The requesting owner completes their own enrollment. Only owner or current workspace administrator can revoke a device; only owner can rotate. Existing five MCP tools do not change.

The client generates independent random32-byte canonical base64url verifier and future token and MUST retain pending values in its OS secure store BEFORE exchanging. Begin supplies a1–80-byte non-control label, SHA256(verifier ASCII) as canonical base64url challenge, unique requested actions including memory:read, and stable1–128 ASCII operationKey. Allowed device ceiling is memory:read/capture, proposal:write and review:read; it never includes human semantic approval/admin/raw-evidence powers. Current owner role must allow requested/approved actions. At most8 live credentials or unexpired pending enrollments per owner/workspace. Challenge lifetime10minutes, issued credential30days, zero offline/expiry/revocation grace. These are bounded defaults, not production SLOs.

Admin approves exact enrollmentId/expectedRevision/actions; completion supplies enrollmentId/verifier/token. Current owner, approver, identity bindings, grants and deadline are checked under transaction locks. Secrets cross into SQL only as hashes; public command metadata is stored separately. Completion atomically creates device identity, scoped membership/grant, owner/current-credential linkage, audit and public receipt. The credential remains kind=device and every request intersects CURRENT owner/device authority. Device captures are evidence, not approved knowledge. Public receipts never contain the raw token/verifier or grant human powers. Approval stale-revision conflict requires status refresh, not an automatic new approval.

Rotation supplies deviceId/expectedGeneration/new independent token/operationKey using a current signed HUMAN session, including after credential expiry. Revocation supplies deviceId/operationKey. All old generations are invalidated atomically; explicitly revoked devices cannot rotate. Exact begin/rotation/revocation retries return historical public receipts, never reactivate credentials; changed payload with reused key conflicts. Complete can reconcile the exact proof/token inside its enrollment deadline, returning its original receipt even if a later generation has replaced it. A receipt proves that operation, NOT current credential validity; confirm current authenticated access. HTTP401 requires sign-in;403 requires current scope/grant checks, not a credential bypass;409 requires reconciliation; unknown/deadline requires original-key/status reconciliation rather than assuming rollback. Do not place secrets in URLs/argv/logs or swap a human JWT for a device token.

List returns only caller-owned devices, at most100 newest records with explicit `truncated`; it is not a total inventory or administrative content projection. Status permits owner or current explicit workspace admin, with foreign/missing indistinguishable. Successful mutations append immutable redacted audit; rejected commands roll back without an audit mutation. Schema/service, actual signed HTTP/MCP and server restart are locally exercised. A usable OS-store client/platform reconnect witness is Story8.3, not supplied by this server API; no plaintext-file fallback or actual deployed device acceptance is claimed here.

## Backup and recovery harness

`src/recovery-target.ts` and `src/recovery.ts` expose an explicitly isolated developer recovery harness. Only a target capability created in the current process by `createRecoveryTarget()` is accepted; arbitrary URLs, existing resources, copied objects and caller-controlled container names are not accepted. These capabilities are NOT durable credentials and cannot be reconstructed after the process exits. Docker resources are uniquely labelled/owned, pinned and resource-bounded; a dedicated bridge is not a promise of network-egress isolation. Call `closeRecoveryTarget()` in a finally block for every owned target.

After initialization, `backupRecovery(target,ownedOutputDirectory)` returns a unique manifest path, not a date-overwritten filename. The single exported-snapshot dump is streamed, private, bounded to 256 MiB / 60 seconds, and includes canonical data plus derived vectors. Manifest includes actual archive bytes/hash, schema digests, model metadata and source inputs. Preserve archive AND manifest, protecting both as confidential data; they are not encrypted or cryptographically signed by this helper. Failed/partial backups are removed and never count as success.

Create a second fresh target capability and call `restoreRecovery(newTarget,EXACT_MANIFEST_PATH)`. Restore rejects forged capabilities, nonempty/foreign targets, concurrent same-target writers, corrupt/missing/path-traversing/incompatible archives and unexpected resource mutation. It hashes a private snapshot of actual selected bytes before a single-transaction pg_restore. Application login remains disabled until a separately injected fresh restricted credential is configured. A process failure after role creation can leave a NOLOGIN role even if restore rolls back; discard that owned fresh target rather than blindly retrying. Verify real canonical evidence/receipt/lineage/audit/vector data, restricted-role reads and native HTTP retrieval before considering recovery usable; a matching sidecar alone is insufficient.

Fresh target creation and restart wait for actual SQL readiness within a 30-second elapsed-time budget, not a fixed number of fast connection failures. Deadline abort cancels the active readiness query and closes its connection; no late probe success is accepted. Startup failure remains a sanitized failure, not a usable target. This deadline is separate from individual bounded Docker commands and archive dump/restore budgets.

This helper does NOT back up an existing deployment or provide an operationally approved production disaster-recovery plan. The runbook and automated isolated witness prove local current-schema behavior only. Production backup destination, encryption, retention, schedules, least-privilege credential delivery, onboarding and restore authority require separate approved configuration. Historical shared AD-71 databases and legacy 1024/4096-vector examples are not this runtime.
