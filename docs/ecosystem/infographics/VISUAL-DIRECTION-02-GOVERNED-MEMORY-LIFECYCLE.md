## Key visual decision

Build one calm, editorial lifecycle rail—not a software interface. Distinguish **evidence**, **proposal**, and **canonical knowledge** with shape, label, icon, and color; route **Supersede** back to canonical knowledge so revision visibly preserves history.

The approved brand references establish Cream as the canvas, Ink as the primary reading color, bold geometric forms as anchors, and Blue/Orange/Green as meaning-bearing accents. The earlier flow graphic is useful for left-to-right orientation, but its glow, “HUMAN GATE” shorthand, generic Promote step, and absent wordmark must not carry forward.

## Communication hierarchy and scan path

Target comprehension: 30–60 seconds.

1. **0–5 seconds — Identity and idea:** wordmark, eyebrow, headline, and introduction.
2. **5–20 seconds — State change:** follow the central rail from captured evidence to proposal, governance review, canonical knowledge, and scoped retrieval.
3. **20–40 seconds — Meaning:** read the five numbered explanations attached to their corresponding rail groups.
4. **40–50 seconds — Revision:** follow the **Supersede** return loop to the canonical state; the prior version remains visible.
5. **50–60 seconds — Action:** read the bottom-line takeaway and call to action.

Hierarchy order: headline → process rail → five explanations → takeaway → action. The wordmark identifies the source but does not compete with the headline.

## Exact approved visible copy

Copy below is locked. Do not rewrite, abbreviate, or add labels.

**Eyebrow:** Governed memory lifecycle

**Headline:** How Evidence Becomes Knowledge

**Introduction:** Allura separates recorded activity from approved knowledge through a governed, tenant-scoped lifecycle.

**1. Capture evidence**

Activity is appended as an evidence event and projected for episodic search.

**2. Evaluate and propose**

Scoring may create a promotion proposal. A proposal is still evidence—not approved truth.

**3. Record the decision**

Governance records the actor, rationale, decision, and source. Human approval is the accountable boundary; automated curator behavior remains under review.

**4. Materialize knowledge**

Approval authorizes or queues a canonical semantic version. Materialization is not universally instantaneous.

**5. Retrieve and revise**

Approved knowledge is retrieved within tenant scope. Updates create a new version and preserve prior history through supersession.

**Process labels:** Capture → Score → Propose → Governance review → Authorize or queue → Canonical knowledge → Scoped retrieval → Supersede

**Required metric labels:** None

**Bottom-line takeaway:** Treat activity as evidence until governance authorizes durable knowledge.

**Call to action:** Check approval state before reuse.

## Layout and flow

- Use a 12-column grid with 160 px outer margins, 32 px gutters, and an 8 px spacing base.
- **Header, top 22%:** real Allura wordmark at top right; eyebrow, headline, and introduction left-aligned across columns 1–8.
- **Lifecycle, middle 51%:** a single left-to-right rail across columns 1–12. Group the eight labels into five numbered content zones without collapsing any label.
- **Evidence state:** Blue circular token with a document/event icon; use a dotted trailing texture to signal recorded activity. **Capture** and **Score** remain inside this evidence zone.
- **Proposal state:** Orange diamond token with a document-plus-decision icon. **Propose** must sit visibly before **Governance review**; it cannot resemble approved knowledge.
- **Decision boundary:** Orange vertical rule with a ledger/check icon and the exact label **Governance review**. Do not use a gate, person silhouette, or the words “human gate.”
- **Materialization:** **Authorize or queue** branches into two parallel strokes that reconverge at the canonical state. This depicts permitted timing without implying universal instant promotion.
- **Canonical state:** Green arch/rounded-rectangle token with a version-stack icon and the exact label **Canonical knowledge**.
- **Retrieval state:** Ink outlined tenant container with search icon and the exact label **Scoped retrieval**.
- **Supersession loop:** a thick return arc labeled **Supersede** travels from retrieval/revision back to a new canonical version. Keep the prior canonical card behind it at 45% opacity with an intact outline; never erase or overwrite it visually.
- Attach each numbered explanation to its relevant group using short Ink leader lines. Alternate cards above and below the rail to preserve rhythm and avoid a dense row of panels.
- **Footer, bottom 16%:** takeaway in a Cream-on-Ink band; call to action at its right edge. Keep all production/legal metadata off this master unless separately approved.

Use Ink on Cream for body copy. Use Cream on Blue or Ink only. Use Ink—not Cream or white—for text placed on Orange or Green. Never communicate status through hue alone.

### Typography

- **Aeonik Bold:** headline, 148 px/0.98 line-height at 3840 px; 74 px minimum at 1920 px.
- **Aeonik Medium:** eyebrow and section headings, 42–48 px/1.1.
- **Aeonik Regular:** introduction and section explanations, 32–38 px/1.35; never below 30 px at 3840 px.
- **IBM Plex Mono Medium:** process labels only, 27–30 px/1.2 with modest tracking; never use it for paragraphs.
- Sentence case throughout. Reserve all caps for no visible copy in this piece.

### Shapes, icons, and spacing

- Use flat geometric shapes with 20–28 px corner radii, 3–4 px Ink strokes, and no glow, bevel, glass, or 3D effects.
- Use one consistent 3 px outline icon family. Icons clarify; labels carry meaning.
- Status grammar: evidence = circle + dotted trail; proposal = diamond + split outline; canonical = arch/rounded rectangle + version stack; retrieval = outlined tenant container; supersession = return arc + visible prior version.
- Keep at least 48 px between text and any rail/shape, 64 px between adjacent state groups, and 96 px between header and lifecycle.
- Connectors use solid lines for progress, double/parallel lines for authorize-or-queue, and a return arc for supersession. Arrowheads must remain visible in grayscale.

### Accessibility and non-color cues

- Meet WCAG 2.1 AA contrast: 4.5:1 for body text and 3:1 for large text and meaningful graphical boundaries.
- Every state uses four cues: exact text label, unique geometry, unique icon, and color.
- Maintain reading order left-to-right, then explanations, then footer; alt text follows the same order.
- Validate at 1920 × 1080, 50% zoom, grayscale, deuteranopia simulation, and on a standard laptop display.
- Do not place paragraph copy over patterns, connector lines, or colored shapes.

## Strict avoid list

- No Neo4j.
- No production, production-ready, deployment, or status claims.
- No ports, metrics, percentages, gauges, or performance indicators.
- No implication that approval always promotes instantly.
- No “human gate” shorthand; preserve the approved accountable-boundary sentence.
- No glowing sci-fi UI, neon, glassmorphism, dashboards, or device chrome.
- No extra logos; use only the supplied, unmodified Allura wordmark.
- No invented nodes, integrations, agents, clients, labels, or capabilities.
- No process collapse that makes evidence, proposal, and canonical knowledge look equivalent.
