# Story 11.9 — SOC2 Technical Readiness

**Title:** Implement technical controls for SOC2 Type II readiness
**Priority:** P1-High | **Complexity:** Medium | **Agent:** Woz + Hightower
**Traceability:** Epic 11 → B7 (SOC2 mode), B15 (BYOK), B21 (RBAC), NFR1-NFR7 → security tests → `bun test src/lib/auth/ src/lib/security/`

## User Story

As an Allura operator deploying for enterprise customers,
I want the technical controls in place for SOC2 Type II audit readiness,
So that an auditor can verify security, confidentiality, and processing integrity from the codebase.

## Context

Allura's architecture is already SOC2-friendly (append-only traces, HITL gates, RBAC, tenant isolation, SUPERSEDES versioning). This story closes the remaining technical gaps. Organizational controls (written policies, pen testing, auditor engagement) are documented as follow-ups, not code tasks.

## Acceptance Criteria

### AC1: Encryption at Rest

**Given** PostgreSQL and Neo4j store sensitive memory data,
**When** the system is deployed,
**Then** PostgreSQL uses `pgcrypto` extension or volume-level encryption.
**And** Neo4j uses encrypted store configuration.
**And** `.env.example` documents `ENCRYPTION_KEY` requirement.
**And** BYOK pattern: encryption key is provided by operator, not hardcoded.

### AC2: Encryption in Transit

**Given** services communicate over network,
**When** connections are established,
**Then** PostgreSQL connections require `sslmode=require` (reject plaintext).
**And** Neo4j bolt connections use `bolt+s://` (encrypted).
**And** MCP HTTP gateway requires HTTPS in production (HTTP allowed only in dev).
**And** connection strings in `.env.example` document TLS requirements.

### AC3: MFA Enforcement for Privileged Roles

**Given** Clerk handles authentication,
**When** an admin or curator logs in,
**Then** MFA is required (Clerk MFA policy enforced for these roles).
**And** viewer role MFA is recommended but not required.
**And** the policy is documented in `docs/allura/RISKS-AND-DECISIONS.md`.

### AC4: Vulnerability Scanning in CI

**Given** the project uses Bun for dependency management,
**When** CI runs,
**Then** `bun audit` (or equivalent) checks for known vulnerabilities.
**And** critical/high vulnerabilities block merge.
**And** results are logged as CI artifacts.

### AC5: Secret Redaction Verification

**Given** events are logged to PostgreSQL `metadata` JSONB,
**When** any event is written,
**Then** a redaction check ensures no field matching `password`, `secret`, `api_key`, `token`, `credential` patterns exists in metadata.
**And** violations are logged as `security_violation` events and blocked.
**And** the check runs as a database trigger or application-layer guard.

### AC6: Data Deletion Endpoint (GDPR/CCPA)

**Given** a user requests deletion of all their data,
**When** `DELETE /api/memory/user/:userId?groupId=allura-*` is called by an admin,
**Then** all memories for that user_id are soft-deleted (append-only — deletion events added).
**And** Neo4j nodes are marked deprecated.
**And** a `user_data_deletion_requested` event is logged with admin actor.
**And** the response confirms count of affected records.

### AC7: Model Version Logging

**Given** an AI inference is made (chat, scoring, embedding),
**When** the result is stored,
**Then** the event metadata includes `model_id` and `model_version`.
**And** this enables auditors to trace which model version produced which output.

### AC8: Security Headers

**Given** the Next.js app serves HTTP responses,
**When** any response is sent,
**Then** it includes: `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Content-Security-Policy` (restrictive).
**And** headers are set in `next.config.ts` or middleware.

### AC9: SOC2 Evidence Documentation

**Given** an auditor requests evidence,
**When** the evidence pack is assembled,
**Then** it includes:
- Tenant isolation proof (schema constraint SQL + test results)
- RBAC configuration (Clerk role setup + permission profile tests)
- Append-only proof (no UPDATE/DELETE on events table — migration SQL)
- HITL gate proof (promotion mode config + curator approval flow)
- SUPERSEDES versioning proof (Neo4j relationship queries)
- Encryption configuration (connection strings, pgcrypto status)
- CI vulnerability scan results
- Access control test results

**And** the pack is generated by `bun run soc2:evidence` script.

## Implementation Notes

- Create `src/lib/security/` directory for redaction checks, security headers, evidence generator
- Add `soc2:evidence` script to package.json that generates the evidence pack
- Security headers go in `next.config.ts` `headers()` function
- Model version logging extends existing event metadata (add `model_id` field)
- BYOK: use `ALLURA_ENCRYPTION_KEY` env var, document rotation procedure
- Do NOT implement organizational controls in code (policies, training, vendor management) — document as follow-ups
