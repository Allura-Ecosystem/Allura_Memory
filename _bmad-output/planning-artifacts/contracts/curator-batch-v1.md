# Curator batch v1 — bounded adopted feature contract

Disposition: adopted local feature design under the approved November 5 Correct Course. Specified, not implemented, tested or deployed. Story 4.5 owns exact strict DTO/SQL design finalization and test-first implementation; 6.6 consumes its versioned contract. Existing authority-v1, persistence-v1, decisions.ts and DOC-06 remain controlling. No live permission or schema change follows from this file.

## 1. Scope and authority

Use the existing Bun/TypeScript/PostgreSQL gateway, restricted transactions, immutable proposal/evidence rows and decision service. No new service/database, arbitrary executor, embedding dependency, role or human impersonation.

Preparation requires current scoped review:read and a transport-compatible human or ordinary curator/owner-linked machine whose existing credential, delegation and grant intersections permit that action. Device and selected-only ceilings remain unchanged. Explicitly deny machine actions if its current ceiling does not include review:read; do not widen a credential to make acceptance pass. Raw/unlinked evidence still needs its separate right. A preparation operation can create only bounded operational review-set metadata; it cannot create a proposal, semantic version, decision or work transition.

Approve/reject/request_evidence remain independently eligible genuine-human operations with review:read and review:approve, current membership/grants, requester/producer/source-author exclusions, rationale, linked evidence and exact reviewed version. No general close/merge/withdraw or automatic durable correction is added. Classification is a recommendation, not a decision. Existing correction/restoration decisions retain exact current head/base checks.

## 2. Frozen inventory and finite limits

The new versioned curator surface must be separate from legacy endpoints and the existing five core memory tools. Strict input rejects unknown fields, invalid identifiers, unbounded values and caller-selected actor/authority. Server derives scope/principal. Authenticate before body/private work; current authority is rechecked for every request and transaction.

The first implementation declares bounded strict DTOs for: create/read frozen set, page its members, read exact item/evidence, seal recommendations, inspect receipts/reconcile. Machine transport exposes only preparation/read operations. Genuine-human review uses same-origin signed-human transport and the existing decision service; it is not a bearer approval tool. Exact routes/tool names must be pinned in the initial Story 4.5 design block before its RED and versioned in the consumer inventory; they are not asserted as existing here.

Engineering bounds for v1: at most 256 proposal members in a review set, 1–20 rows per page, 24-hour maximum eligibility for new execution from a sealed set, and no more than four unfinished sets per preparing principal/workspace. These are local safety defaults, not measured product SLOs. Capture the pending/needs_evidence membership and exact immutable versions in one consistent server transaction, sorted by proposal UUID. If a requested complete queue exceeds the cap, return an explicit bounded-coverage limitation and no misleading complete set; a later explicitly selected subset must be labeled partial. Stable scope/principal/set-bound cursors never read a moving queue or disclose foreign metadata. Counts describe this frozen set, not a global population.

A frozen set records server ID, contract version, preparing principal/scope, original operation key and normalized request digest, database creation/expiry, ordered exact member IDs/versions, immutable proposal/evidence identity/content digests and correction/restoration base/head bindings. Creation/replay is bound to the preparing principal; this does not make the independently authorized human reviewer impersonate that principal. Set/item inspection independently checks the current reader's same-workspace review:read and permitted linked evidence; a received set ID alone grants nothing. Issue each reader its own principal-bound cursor. The reviewer independently satisfies decision eligibility for each selected proposal, without inheriting the preparer's rights. Preserve full permitted source content for review through exact evidence reads; a truncated list summary is never approval-ready. Do not duplicate arbitrary raw source content into broad activity/audit projections. Missing/inaccessible sources create explicit gaps.

Create-key replay is principal/scope/operation bound, returns the original set/receipt under current authorization, and rejects changed inputs. Expiry prevents new decisions from the set, not original committed-result reconciliation or deletion of history. Retention of committed receipt links is append-only; no cleanup in this milestone destroys decision/replay evidence.

## 3. Review and decisions

Review all member/evidence pages, classify ready-to-keep, duplicate, superseded, dated-history, conflict or unsupported, and seal exact proposed wording/action/rationale/evidence/base bindings into an immutable digest-addressed review revision. Recommendations reference existing immutable proposal text; changing semantic wording requires its own valid pending proposal/review rather than replacing approved content inside a batch payload. Corrections remain proposals until human-approved.

One understandable grouped human review shows full selected content, evidence, recommendations and exceptions, and binds the exact sealed revision/selection. The actual independently eligible human performs genuine signed same-origin decisions; neither the preparing agent nor connection consent can manufacture the approval. The supported browser may dispatch bounded per-item requests after one explicit selection/confirmation; it must never pass a human credential to the agent. Each item's eligibility is checked separately. Someone ineligible for one item gets an honest independent-reviewer handoff.

Reuse existing decision-v1 normalized payload/digest, immutable receipt bytes and transaction checks. Derive stable per-item operation keys once and retain them across restart; the batch digest is additional linkage, not a replacement for existing decision digest semantics. A new decision must match the frozen/sealed proposal revision and current pending state/base/head. New arrivals and changed content stay outside old authorization. Never silently refresh a revision or auto-rebase. An independent legitimate single-item decision outside a batch remains governed by its existing contract; do not rewrite that service's historical receipts.

## 4. Deterministic reconciliation

PostgreSQL review metadata/links are the operational authority. Progress is derived from exact member identities and authoritative receipts, not model claims or semantic memory. Per-item outcomes distinguish committed approve/reject, pending-needs-evidence, conflict, denied, failed-known-rollback, not-attempted and unconfirmed. A request_evidence receipt is a held item, not cleared backlog. Match each receipt's exact proposal/action/reviewer/version and resulting semantic record where applicable.

Completion is per item, not a whole-batch transaction. Do not hold authority locks across human review/network waits or all batch items. Current authority/revocation and proposal/base state are checked within each short protected transaction. Concurrent batches produce at most the permitted service decision; a losing attempt reconciles or conflicts without a duplicate effect. Lost response is unknown until original-key receipt readback; no fresh-key blind retry. Fresh-process continuation reuses stored operation identities and does not repeat verified effects. Revocation stops uncommitted actions; committed history remains.

Report coverage and outcomes programmatically against frozen membership; separately observe new arrivals/current queue. Missing receipt/read access leaves an unconfirmed result. A fully reviewed set can still be awaiting human decisions or partially completed. Readiness and completed coverage are action-specific. No-change maintenance creates no capture or proposal solely for a tick. This contract does not schedule jobs or use Epic 12's pinned executor.

## 5. Compatibility, validation and rollout

Preserve five-tool and existing single-item decision schemas unless an explicitly versioned compatibility change is adopted. Additive migration only after existing inventory discovery; preserve original migration/source pins and genuine historical replay. Changes to pinned executor inputs require their own immutable revision/upgrade proof; no weakening pins to make tests pass.

Actual restricted-DB/API/client tests must cover multi-page mixed sets, later arrival/revision drift, wrong scope/actor, source evidence restrictions, same-key replay/conflict, expiry, self/machine decision denial, concurrent decisions, rollback, lost response, fresh process and mid-run revocation. Final completion includes exact semantic readback/current retrieval. Register all new cases in canonical runner and independent CI inventory without dropping existing cases/floors/budgets. Current shared 13.2 verifier failure is not waived by these specs.

Local implementation acceptance, installed-client integration, actual-human usability and separately authorized deployment/release remain distinct. Standing authorization, machine reject/close/promote, scheduler/source checkpoints, general coding execution and automatic work-item status are excluded.
