# Story 9.5 — handle cleanup in one understandable journey

## Outcome, design and scope

When a person says “handle my pending review,” Bahari starts the supported task in the verified space, reviews full evidence, presents one concrete grouped decision when required and reports only verified outcomes and remaining exceptions. Sources: [approved Correct Course](../sprint-change-proposal-2026-11-05-bahari.md), BAH-R01–R07, current DESIGN-ALLURA/operator contract additions, FR-E1/E2/E4, DOC-06 and NFR-6/8. Reuse accepted 9.1–9.3 surfaces and current Allura assets/Plex/tokens; no new brand/chat engine/template or replacement operator dashboard.

Depend on implemented 4.5 and compatible 6.6 contracts before promising callable controls. Flow/copy and bounded component work can be specified earlier; actual complete journey cannot. Source map: current dashboard React/transport/view/contracts, review/evidence/receipt inspector and browser/packed-server tests. Exact retained screen/revision and allowed files are bound at admission. The five plain-language destinations are organization labels, not assumed new working routes.

## Acceptance criteria

- **BAH-95-01:** current verified space and connection/source account status are understandable. Reuse authorized settings, ask only missing choices, never silently merge/switch spaces or select every account. An unavailable name/context source is an honest setup limitation.
- **BAH-95-02:** conversation initiates supported frozen review; overview shows covered sources and useful outcomes, not raw queue/tool counts as success. Distinguish source notes, pending proposals and approved current knowledge.
- **BAH-95-03:** one grouped exact review shows full wording, sources/dates, before/after when applicable, recommendations and exceptions. Exact selection and genuine independently eligible human confirmation use existing policy. A changed revision leaves old authorization; arrivals remain outside. Ineligible requester receives a specific reviewer handoff, not repeated prompts to approve their own work.
- **BAH-95-04:** activity reports completed, pending-needs-evidence, conflict, failed-known-rollback and unconfirmed separately with item receipts/readback. Timeout does not mean rollback or Done. No classifying-as-execution, zero-queue vanity goal, source deletion on rejection or universal undo/erasure promise.
- **BAH-95-05:** source selection and action authority stay separate. “Curate for me” is unavailable under current independent-human policy. “Review every change” is selectable only if its actual pre-persistence staging boundary exists. No attractive unsupported toggle or fake reconnect/link.
- **BAH-95-06:** keyboard operation, screen-reader control/status names, textual non-color statuses, consequential confirmation, retained/returned focus after batch actions, and 200% zoom all work in actual browser journeys. Technical scopes/IDs/tools are optional support details, not the ordinary task.
- **BAH-95-07:** synthetic 25-member mixed set spans pages; later arrival and revision drift; real denied/machine/self review, conflict, partial/lost commit, restart and revocation variants pass through actual client/server. Restricted-space rules stay local, no global XTERRA restriction.
- **BAH-95-08:** after genuine approval, later authorized retrieval returns correct current wording with source/history retained. Actual representative nontechnical human task acceptance is recorded separately from automated browser/component checks and from separately authorized deployed acceptance.
